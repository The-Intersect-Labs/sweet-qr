# SweetQR

A polished, **local-first** QR code toolkit. Create QR codes for links, Wi-Fi, contacts, email,
phone, SMS and locations; style them; export as PNG or SVG; and scan codes with a camera or from
an image.

There is no backend, no account and no analytics. Saved codes, logos, settings and scan history
live in your browser's local storage, and camera frames and uploaded images are decoded on-device.

## Tech stack

| Concern | Choice | Why |
| --- | --- | --- |
| Framework | Nuxt 4 + TypeScript | File-based routing, auto-imports, first-class composables and a single build for both dev and production. |
| Styling | Tailwind CSS v4 + shadcn-vue | Accessible, unstyled-first components we own outright, themed with CSS variables. Indigo/violet accent on neutral surfaces. |
| QR generation | [`qr-code-styling`](https://github.com/kozakdenys/qr-code-styling) | The only library that covers the whole customisation brief in one place: dot styles, corner styles, fg/bg colours **and gradients**, error-correction level, margin, centre logo, and `getRawData('png' \| 'svg')` for both export formats. Its only runtime dependency is `qrcode-generator`. |
| QR scanning | [`jsqr`](https://github.com/cozmo/jsQR) | Zero dependencies, QR-only (which is all this app needs), and the same API for both inputs — camera frames and uploaded images both become `ImageData`, so there is one decoder and one code path. |
| Utilities | VueUse | Clipboard, media queries, device helpers. |
| Theme | `@nuxtjs/color-mode` | Class-based dark mode with no flash of the wrong theme. |
| Offline | `@vite-pwa/nuxt` | Manifest + auto-updating service worker, so the app installs and works offline. |
| Tests | Vitest | Fast unit tests over the payload/codec/validation layers. |

### Why not X?

- **Pinia** — three collections of local data do not need a store library; `useState` plus one
  persistence plugin is smaller and easier to reason about.
- **vee-validate + zod** — the QR type registry already describes each field and its rules, so
  validation derives from that single source of truth in ~50 lines.
- **`html5-qrcode` / `@zxing/*`** — `html5-qrcode` brings its own DOM UI (hard to style to the
  design language) and ZXing carries multi-format support this app does not need.
- **`@vite-pwa/assets-generator`** — it rasterises through `sharp`, whose native binary fails to
  load on this machine (`ERR_DLOPEN_FAILED`). Worse, when that happens the PWA plugin skips icon
  generation *silently* and ships a manifest with no icons. Icons are instead generated by
  `scripts/generate-icons.mjs`, which encodes PNGs directly with `zlib` and has no native
  dependencies.

```bash
npm run dev          # http://localhost:4000 (PORT is set in .env)
```

## Architecture

### One registry drives everything

`app/lib/qr/registry.ts` defines the eight QR types — their label, icon, form fields, defaults and
payload builder. That single definition drives the generator form, validation, the type filter in
the library, and the scan-result detection. Adding a QR type means adding one entry, not touching
eight components.

- `app/lib/qr/codec.ts` — the format layer. **Build and parse for every format live together**, so
  the escaping rules used to encode a Wi-Fi password are the same ones used to decode it.
- `app/lib/qr/validate.ts` — walks the field definitions, plus a per-type hook for cross-field
  rules (a contact needs a first *or* last name).
- `app/lib/qr/parse.ts` — turns an arbitrary scanned string into a typed result with declarative
  actions. The UI renders `fields` and `actions` and never inspects raw strings.

### Rendering

`buildQrOptions()` (`app/composables/useQrRenderOptions.ts`) is the single mapping from style state
to renderer options, used by **both** the live preview and the exporter, so what you see is what you
download. Sizes differ between the two, so pixel-based values (margin, logo padding) are scaled by
the resolution ratio to keep proportions identical.

The preview renders at a fixed 1024px internally and is scaled with CSS. `qr-code-styling` emits an
SVG with fixed `width`/`height` attributes, so the component adds a `viewBox` after each render to
let it scale inside a fluid container.

### Persistence

`app/plugins/persistent-state.client.ts` owns every localStorage-backed collection. Wiring lives in
a plugin rather than in the composables so the watchers are app-scoped — a composable-scoped watcher
would stop persisting as soon as the component that first called it unmounted. Reads are forgiving:
an older or hand-edited payload is repaired onto current defaults rather than throwing. Writes
report a recoverable error if the storage quota is exceeded.

## Security notes

- **Scanned links are never opened automatically.** Open is always an explicit click.
- Payloads using `javascript:`, `data:`, `file:` or `blob:` schemes are flagged as unsafe and offer
  only a "Copy payload" action — no Open action is produced at all.
- Opened links use `noopener,noreferrer`.
- All scanned payloads are rendered through Vue interpolation, never `v-html`.
- Logos are downscaled to 256px and re-encoded to WebP before being stored, to protect the
  localStorage quota.

## Verification

What is covered by automated checks:

- `npm run typecheck` — clean.
- `npm test` — payload round-trips (build → parse) for all eight types, escaping edge cases
  (Wi-Fi SSIDs containing `; , : " \`, vCard values containing newlines/commas), scan-result
  detection including unsafe schemes, validation rules, and the render-option mapping
  (margin scaling, gradient degree→radian conversion, transparency, logo handling).
- `npm run build` — clean production build; service worker, manifest and icons are emitted.
- axe-core accessibility audit on all six pages — **0 violations**.
- Browser-verified end to end: live preview updates, gradient presets, save/rename/favourite/
  duplicate/delete/edit round-trips, persistence across reloads, PNG export (a real 1024×1024 PNG)
  and SVG export (valid markup with `viewBox`), and a full round trip of **export → upload → decode**
  with correct content-type detection.

### Known limitations

- **Camera scanning was not verified with a real camera.** This environment has no camera device, so
  only the permission-denied error path and the capture/scan UI states were exercised. The decode
  path itself shares the exact same `jsQR` call as the upload path, which *is* verified end to end.
- **HEIC/HEIF photos** cannot be decoded by browsers. The app detects them and explains the fix
  rather than failing silently.
- **Torch** requires a device and browser that support it; the control is hidden when unsupported
  (notably iOS Safari).
- The camera requires a secure context — `localhost` during development, HTTPS in production.
