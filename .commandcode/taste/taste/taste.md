# Taste
- Prefers additive, low-blast-radius changes: new features should slot into existing seams rather than restructure or "shift things around" in the app. Reuses existing abstractions/tests instead of introducing parallel concepts (e.g. treating dynamic QR codes as a hosting axis, not a new QR type). Confidence: 0.6
- Do not use the browser (agent-browser) to verify small or contained fixes — the user tests those themselves. Reserve browser-based verification for substantial features or when explicitly asked. Confidence: 0.9
- For contained changes, typecheck + the test suite are the expected verification bar; skip `npm run build` unless the change is substantial or the user asks (e.g. SSR-bundle confirmation). Confidence: 0.7
- Solicits the agent's honest product/direction judgment on whether something is worth building ("do you think it's worth adding?") — values candid, opinionated recommendations (including arguing against a feature) rather than just execution. Confidence: 0.5
- Not pursuing monetization; treats the app's privacy-first, local-only positioning (no backend, no accounts) as a core value to protect, and declines features that would trade that away (e.g. server-hosted dynamic/managed QR codes) even when they're table-stakes for competitors. Confidence: 0.6
- Prefers roomier, more generously padded UI controls over dense/compact ones — asks for global size increases (e.g. "increase the general button size and add more padding") rather than tweaking a single control. Confidence: 0.5
- Defaults to keeping the app simple: pushes back on speculative or "nice to have" features with "do we need to do this?" and declines scope that isn't backed by real evidence of need. Prefers small, high-value additions over new subsystems (e.g. favors a one-line `navigator.storage.persist()` over building export/import). Confidence: 0.6
